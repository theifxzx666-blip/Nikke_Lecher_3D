# 莱彻 3D 查看器 · NIKKE 主线全 BOSS

把客户端里**全部 49 个 BOSS 型号**（89 个按钮变体 / 112 个 glb / 497 MB）从资源包直接导出成 glTF，
在浏览器里旋转、缩放、逐部件拆解、线框查看。**其中 32 个型号带真骨骼动画**（36 个动画变体），
打开就自动播，不是 OrbitControls 那种「动」。

- 在线地址：<https://theifxzx666-blip.github.io/Nikke_Lecher_3D/>
- 参考站 nkas 的同类页面用的是静态烘焙网格（`skins=0 / animations=0`）；
  本项目每个模型都尽量取真实的 skin + animation。


`xba003_dmtr` / `eba002_hsta`。`?glb=` 可以直接点名任意文件（包括不进按钮的 16 条表演动画）。

## 采集范围与判据

`MonsterModelTable` 里 **Grade=5 且 Size=4** 是该表唯一的 BOSS 级档位，共 69 个型号；
剔除拦截战 / 联盟突袭 / 单人突袭 / 合作 / 模拟室 / 教学 / 测试 / 全息 / 黄金等非剧情变体后 47 个，
再加本期新增的 `xba004_dmtr`（怀旧）与 `xbg006_anmi`（胜利女神），共 **49 个版本 / 31 个 BOSS 本体**。

同一个本体在不同剧情线会有多个变体（例：捍卫者 `eba003` 有 A.N.M.I. / D.M.T.R. / H.S.T.A. /
P.S.I.D. / Z.E.U.S. 五个），列表里都保留 —— 它们的贴图与配色不同，属于不同版本的同一只莱彻。

**章节号没有标，这是有依据的取舍**：客户端里 `CampaignStageTable` 的 `field_monster_id`
只是该关的巡逻杂兵（49 章 BOSS 关给的是 `23100201`，指向「三体」），关底 BOSS 由服务器战斗数据下发，
静态表里不存在 `stage → boss 型号` 的映射。硬标章号只能靠剧情文本猜，上一版就是因为这个把
49/50 章的两只挂反了。所以现在按「型号 + 阵营」组织，不编章节。

## 部件完整性审计

用户反馈「缺部件」，逐项查过，结论分三层：

**① 几何一个没漏。** 把 49 个 BOSS 的 `SkinnedMeshRenderer` 子网格总数，与部署清单里
static 变体的 glTF primitive 总数逐一对比：**49/49 完全相等，0 处缺失**。
（口径：Unity 的 `m_SubMeshes` 一个子网格 = 一个 primitive。）

**② `mba002` 的包围盒被幽灵件撑爆，看起来像「主体丢了」。** 它的包里 23 个 SMR 中有
10 个 `eye_l_*` / `eye_r_*`（材质 `nieye`），各只有 10 个顶点、**零厚度**、只绑 1~2 根骨骼，
位置却被摆在 `y≈130 / z≈-375`，离主体近 400 单位。这些在游戏里不是几何体，而是给 shader
投影到脸上的贴片。原样导出后：

- 包围盒纵深变成 **405.7**，相机被推到三百多米外，122×27 的主体只剩画面里一小块；
- 画面上方多出两片飘着的「小蝴蝶」。

修法：导出时按材质名跳过（`export(..., skip_mats=('nieye',))`），并在算取景框时
排除「零厚度 + 顶点少 + 距离远」的 primitive。修复后 bbox 122.7 × 39.8 × 33.6，主体占满画面。
全量扫描确认**只有 `mba002` 一个**有这个问题。

**③ 动画版一度全都不见了，这是真 bug。** 批量导出脚本对每个型号调用 `export(tag, phase, None)`，
第三个参数 `clip_name=None` 会让 `want_skin = False` —— 既不出 skeleton 也不出 animation，
产出的是 `_static` 烘焙网格。所以第一版 53 个文件全是 `nodes=1 / skins=0 / animations=0`。
现在按主型号重新匹配动画包，导出 36 个带 skin 的文件，实测 `skins=1 / animations=1`、
骨骼通道 4~1513 条，并在浏览器里用「骨骼签名」（每根骨骼 local position 加权求和）验证
t=0 与 t=mid 两帧确实不同 —— 光看 bbox 判断不了：`THREE.Box3.setFromObject` 对
SkinnedMesh 取的是 geometry 的静态 boundingBox，蒙皮变形根本不反映到包围盒上。

## 模型怎么来的

`export_glb.py` 从 `SkinnedMeshRenderer` + `MeshHandler` 取顶点/UV/三角形/蒙皮权重，
骨骼层级与绑定姿态来自 `Transform` 树与 `m_BindPose`，动画取 `AnimationClip` 的
generic TRS 曲线逐帧采样成 glTF animation channel，贴图按内容 sha1 去重。

踩过的坑都记在项目文档里，最要命的几条：

1. **阶段归属要按变体根判定**。包里 1/2 阶段是两套并列的 `*_1phase_var` / `*_2phase_var`，
   都 `activeInHierarchy=True`。按「最近一个名字带 1phase/2phase 的节点」判会把
   `xba003_1phase_magiccarpet_skin`（名字带 1phase、实际挂在 2phase_var 下）算进 1 阶段。
2. **子网格必须逐块配材质**。`Mesh.m_SubMeshes` 与 `Renderer.m_Materials` 按下标一一对应；
   只取 `m_Materials[0]` 会让 78% 的几何贴上错误图集，表现就是「碎、丢细节」。
3. **IBM 就是 `m_BindPose` 本身**，不要再求逆；朝向修正要左右各乘一次
   （顶点 `A·V`、IBM `A·bindPose·A`，`A = diag(-1,1,-1)`）。
4. **动画绑哪套骨架 ≠ 包名写的阶段**。`anim_eba002_2phase_intro_01` 的 338 个唯一骨骼路径
   **全部命中 `eba002_1phaseAvatar`**；`anim_xba003_12phase_appeanrance`（包名自己就拼错）
   也只绑 1 阶段骨架。按包名取会导出 0 条通道的静态模型，而且不报错。
   导出时加了断言：命中数 `n_hit == 0` 或「路径 ≥ 20 条却命中不到 15%」直接抛错。

## 取景：为什么需要 `framing.js`

有些表演动画会把模型**整体搬走很远**（莉贝雷利奥战败时环状部件炸开到几百单位外）。
按绑定姿态或按整段包围盒取景都会出事：

- 用绑定姿态框 → 后段模型跑出画面，导出 GIF 全是背景，直接报「采样到的颜色太少」；
- 用整段动画的 min/max 并集 → 包围盒被碎屑撑到绑定姿态的 **29 倍**，主体缩成一个点。

`framing.js` 是离线算好的取景表：用 numpy 复算 LBS 蒙皮，逐帧取
**稳健**包围盒（中心 = 顶点分量中位数，半径 = 92 分位距离 ×2），分三种用法：

| 场景 | 用哪份数据 |
|---|---|
| 交互查看 | `bind.size`（绑定姿态的真实包围盒）+ `track[0]` 的中心（第 0 帧的位置） |
| GIF 导出 | `track`：逐帧跟**中心**，但**整段共用一个距离**，半径上限「绑定姿态 × 3」 |
| `camera.far` | `union` 的边长，兜住飞远的碎屑，别被远裁面切掉 |

交互视图为什么不用 `union`（整段并集）：莉贝雷利奥战败会把环状部件炸飞到 `z≈-148`、升到 `y≈78`，
并集框的中心整个被拖走，相机跟着盯到一百多米外，而第 0 帧的模型还在原点 ——
结果主体只占画面一小块，还偏在一角。交互查看就该像游戏里一样：镜头对着角色本体，
动画自己飞出去是演出的一部分。
中心用 `track[0]` 而不是 `bind.center`，是因为登场动画首帧模型在天上
（安尼希利奥 `y≈136`，绑定姿态在地面 `y≈15`），用 bind 中心会看到一片空画面。

为什么 GIF 不逐帧各算距离：试过，镜头会忽近忽远 —— 安尼希利奥登场前两帧被上下裁掉、
后两帧缩成一小块。上限那 3 倍是留给主体的，飞散的碎屑允许出画。

顺带纠正一条曾被写进文档的错误结论：这些大位移**不是**取景问题之外的通道 bug，
而是动画内容本身（环状部件炸开 / 整具下落）。早期试过「元凶通道减去自身首帧值」，
实测与「什么都不做」的包络逐条相同 —— 那些通道首帧值本来就是 0，减 0 等于没减。

### 新模型（没有 framing.js 数据的）走 manifest bbox

`framing.js` 只覆盖当初手工调过的那几个文件。其余 100+ 个 glb 用两条兜底：

1. **`manifest.json` 里每个变体都带 `bbox`**（`[min, max]`，世界坐标），页面 `fit()` 直接用它算。
   动画变体复用同阶段静态版的 bbox —— 静态版顶点已经烘焙到世界，是准的；
   动画版顶点还在 mesh space，`Box3.setFromObject` 量出来的是**未蒙皮**的范围，对不上。
   实测胜利女神 2 阶段因此只占画面四成。
2. **算 bbox 时排除离群 primitive**（零厚度 + 顶点 < 60 + 距中位 > 100）。
   只针对 `mba002` 那 10 片 `nieye` 眼睛贴片 —— 它们把纵深撑到 405。
   不能泛化成「距离超过 N 倍中位尺寸就排除」：胜利女神 1 阶段只有 5 个 primitive，
   中位尺寸很小，泛化规则会把展开态的主体外壳整片丢掉（bbox 从 193×230 掉到 41×24）。

取景半径仍然只取 `max(x, y)`，不取 z（理由见下）。新模型留白系数用 1.1，
有 `framing.js` 的老模型仍用 1.35。

## GIF 导出的四个约束

- 逐帧定格必须走 `canvas.toDataURL`，不能用 `Page.captureScreenshot` —— 后者是异步合成器
  出图，连拍会差一帧。
- 裁剪要用 `framing.js` 的 `track`，不要用整段并集（理由见上一节）。
- `AnimationAction.paused = true` 会把 `timeScale` 归零，`mixer.setTime()` 推不动时间轴；
  顺序必须是 `paused=false → setTime() → paused=true`。
- 调色板采样不能太稀。战败动画「边散架边缩小」，采样到非背景像素的概率极低，
  按 `perFrame` 算出的步长会跳过全部有效像素，报「采样到的颜色太少，无法生成调色板」。
  现在采样上限取 12 帧，且稀疏采样拿不到点时做一次稠密重扫。

另外 GIF 的帧延迟以 **10 ms** 为单位，写 79 ms 会存成 70 ms。按目标帧率硬算 duration
会让 4.77 s 的动画播成 4.20 s（快 11%），所以导出的帧数与间隔是反解出来的：
在 10 ms 网格上找 `n × ms` 最贴近原时长、且最接近目标帧率的组合，误差现在都在 0.3% 以内。

画质上用了 2× 超采样（渲染 2 倍分辨率再降采样到目标尺寸），小尺寸不会糊。

## 本地运行

浏览器的跨域限制会让 `file://` 下的 `.glb` 加载失败，需要起一个静态服务：

```bash
python -m http.server 8765 --bind 127.0.0.1
# 然后打开 http://127.0.0.1:8765/index.html
```
